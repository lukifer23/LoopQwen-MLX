# Metal and numerical measurements

The locked environment uses Python 3.12.12 arm64, MLX 0.32.4 and MLX-LM 0.32.2. The M3 Pro has 11 CPU cores, 14 GPU cores and 18 GiB unified memory. Doctor executed a real Metal operation. The original trainer's selected-token projection and native differentiable GDN path remain active. The installed Qwen implementation selects its inference kernel using the training flag. The project specialization preserves FP32 decay and uses the native gradient-capable primitive for training. No custom Metal kernel was added. [Pinned Qwen source](https://github.com/ml-explore/mlx-lm/blob/v0.32.2/mlx_lm/models/qwen3_5.py)

Across 30 long-cache conditions the worst BF16 single-position relative RMS error was 2.30%. A near tie can make short greedy generations diverge, with five mismatching continuations out of six in one chunked condition. Inspect per-case margins, teacher-forced top-1 and free-running counts separately. Across the four 512-position K=3 FP32 comparisons (full/windowed and one-token/64-token chunks), the worst relative RMS was 0.00000304 and top-1 agreement was 100%. This covers the tested sequence and masking regimes. [Long-context measurements](measurements/phase2/long_cache.json)

Sorting distinct prompt lengths into left-padded batches reduced measured K=2 generation from 9.67 to 1.91 seconds for fifteen development prompts capped at 32 tokens. Both methods execute the same maximum decode length. Shape-dependent BF16 differences are possible. On independent-versus-batched requests at K=1, 2 and 3, the worst BF16 RMS was 1.78% and the worst FP32 RMS was 0.00000281 over prefill and four forced continuations. All arms of each comparison use the same batching policy. The measured single-request compute control explicitly performs and times the extra candidates.

The dedicated repeated-GDN test exercises both nonzero LoRA factors on each input, value, gate and output projection. The largest BF16 adapter-gradient discrepancy against reference was 0.73% in the pre-study audit. Repeating the native VJP changed individual gradient tensors by up to 0.12% relative RMS. The reference two-site decomposition had zero measured residual. Replacing right-padding inputs with a different token produced zero change to scored loss.

End-to-end profile timings use one warmup followed by three synchronized complete optimizer updates with actual model weights and LoRA. Shape profiles repeat real token streams as timing inputs. Training-quality evidence uses intact V2 documents. Process RSS, available system memory, swap occupancy and MLX peak allocation are reported separately. Timing dispersion is the median absolute deviation. [Training profiler](../loopqwen/benchmark/phase2_training.py)

During the final evaluation, macOS reached warning-level memory pressure with 1.16 GiB available and 6.61 GiB of occupied swap. Process inspection found one GPU evaluator and its waiting coordinator. The original training path capped MLX's free buffer cache, while the evaluation process inherited MLX's device-dependent default. Seven completed arm files were retained. The evaluator was restarted with a 256 MiB free-buffer cache limit and the same prompts, precision, batch shapes and scoring rules. The next K=2 arm peaked at 2.77 GiB of MLX allocations, reported 0.25 GiB of cached buffers and finished with 7.97 GiB of available system memory. Occupied swap is system-wide and can persist after pressure subsides. Use the separate sequential budget experiment for the matched final latency comparison.

A lightweight coordinator now reads checkpoint pointers and source digests without importing MLX or Transformers. Fresh-process import peak fell from 79.3 to 20.1 MiB on this Mac. The kernel-backed worker lease prevents a second project worker from loading the model concurrently. The study launcher owns its child process group and forwards cancellation. A controlled subprocess check verified duplicate-launch rejection and child termination. Inspect current ownership with `python -m loopqwen resources`.

On 30 development problems from the trained recurrent model, evaluating four sorted documents per batch reduced answer validation time from 1.38 to 0.87 seconds and trace validation from 2.61 to 2.17 seconds. MLX peak rose from 1.57 to 1.99 GiB on answers and from 1.76 to 2.41 GiB on traces. Token counts agreed and NLL changed by at most 0.0019 nats per token. Splitting the output projection into 96-token groups produced a 2.43 GiB trace peak and took 2.27 seconds. It offered no advantage for this workload. New V2 runs can set `validation_batch_size: 4`; the post-selection anchor ablation uses this setting. The historical controls retain their original trainer validation setting.
